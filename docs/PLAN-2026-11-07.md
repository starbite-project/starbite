# Plan of 2026-11-07: the Windows second screen, Starbite OS, drivers

Approved by the user on 2026-11-07. One main track with the phone, five background sessions without it.
The lineup (docs/STARBITE-2-PLAN.md section 0) is unchanged; "Emergency OS" is now called **Starbite OS**.

## Rules for every track

- **One phone (S9 #1), held by the main session.** Background sessions never run adb, fastboot, sbfb.py,
  store-flash.sh, boot-next.sh, the serial shell or anything else that reaches the phone. They send a phone test
  request to the main session: the exact commands, which files, what to expect, what could go wrong, how to undo it.
  Order of phone time: the user's own tests, then the main track, then the sessions.
- **First runs that could hurt the phone only with the user present:** the modem's first start, the heater at full
  power, any new storage-writing tool.
- **Never touch** EFS/CPEFS/PARAM/KEYSTORAGE/PERSISTENT/STEADY/BOTA/DTB/DTBO/GPT/the boot LUNs without a backup that is read
  back and verified. **Never touch MIF or INT clocks** (ACPM DVFS domains 2 = A55 and 3 = M3, plus the GPU's own domain, only).
  **Never test emergency calls** (the emergency number is implemented, never dialled). Never print or commit the IMEI.
  Nothing ever writes the RECOVERY partition.
- Git: commit on your own branch, never push. Commit messages end with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Storage: the Mac's internal SSD has about 7 GiB free and the USB stick SBWORK about 4.7 GiB. Large downloads and
  build trees go to iCloud Drive (`~/Library/Mobile Documents/com~apple~CloudDocs/Starbite-overflow/<track>/`) or
  the lima VM `starbite`. Check `df -h /` before anything over 1 GiB.
- Licences: check each borrowed file (an earlier port: APSL 2.0 for XNU parts, MIT for the rest; brcmfmac: ISC; Samsung and
  LineageOS kernels: GPL-2.0), keep the credits, and note the source at the top of each file.
- Docs: each track keeps its own doc (named below) with what works, what is open and the phone tests it needs.

## Main track: Starbite Link (the main session, with the phone)

Windows 11 on the S9 sees a real extra monitor, "Starbite Display", in Display Settings (an IddCx indirect display
driver), and a Mac app shows it and sends the keyboard and mouse back over USB. Then the same for macOS (Ventura
on the phone) and Linux. Doc: `docs/STARBITE-LINK.md`.

| Step | What | Done when |
|---|---|---|
| L0 | Windows build tools on the Mac (clang-cl, lld-link, the WDK/SDK ARM64 headers and libraries, osslsigncode with the Starbite test certificate) in `tools/win/`; Windows boots on layout v3 | A test driver built on the Mac loads on the phone |
| L1 | USB device mode in Windows: libsb's DWC3 device code as a KMDF driver (or Windows' own UFX Synopsys driver if it ships and works) | The Mac sees the phone while Windows runs |
| L2 | The Starbite app on the Mac + the phone's screen mirrored | Windows shows on the Mac |
| L3 | Keyboard and mouse from the Mac | Windows is usable from the Mac |
| L4 | IddCx virtual monitor, e.g. 1920x1080 | Windows extends onto it |
| L5 | Speed (damage rectangles, compression, later the GPU from track D) | Fine for normal work |

`tools/win/` is shared: the Windows sessions (B, C, D) use it once it lands, and do research, design, portable C
and host tests until then.

## A. Starbite OS (background session)

Ultra-minimal, ultra-low-power, our own code at the lowest level (not Linux), grown from libsb. Not marketed as an
emergency OS, though it is the phone you want in one. Doc: `docs/STARBITE-OS.md`.

- **Kernel:** tasks, a scheduler, interrupts and timers instead of polling, apps at EL0 behind a fixed API (screen,
  touch, files, power, network, phone, camera, sensors), apps as separate files in the store or on the card, so the
  system can be extended.
- **UI:** in the spirit of iPhone Guided Access / Assistive Access: a few big tiles, large type, black OLED
  background, smooth, drawn only on change (the command-mode panel holds a still image by itself).
- **Power:** cores idle in their deepest states; the big cores only for heavy work. Sleep: the first 5 minutes keep RAM
  (screen and CPUs off, instant wake), after that the state goes to storage and the phone powers off (the power key
  resumes). Option "stay reachable" keeps the modem up. Battery estimates learned from the fuel gauge's real current
  in each state.
- **Boot:** under 1 s from the loader to a usable screen.
- **Apps:** flashlight, heater, emergency alarm (loud siren + flashing screen and LED), clock, battery and others.
  The heater runs the big cores at full clock plus the GPU with a hard stop on the battery temperature and charging
  off while it heats (CPU and GPU domains only). Engineer OS's stress test probably stayed cool because it ran on the
  little cores at boot clocks; check and fix it too.
- **Later:** calls and SMS (Shannon CP boot from RADIO, the Samsung IPC protocol; references: Samsung and LineageOS
  kernels' modem_v1/cbd, libsamsung-ipc). The modem's file requests are served read-only from EFS with writes going
  to a copy, never to EFS. Mobile data. Wi-Fi via track C. Camera: front first (raw capture, CPU image processing;
  references: the Samsung kernel and the Galaxy Tab Active3 Linux port).

## B. Windows USB host (background session)

DWC3 host mode on the phone's Windows: Windows' own xHCI/URS drivers if the firmware brings up the PHY, the host
role and VBUS (MAX77705) and ACPI describes the controller (milestone W3 in docs/STARBITE-MASTER-PLAN.md 3.6).
Shares the PHY setup with L1: coordinate through the main session. Doc: `docs/WIN11-USB.md`.

## C. Wi-Fi: a portable Broadcom core (background session)

One portable C core for the BCM4361 over PCIe (the Exynos PCIe controller, firmware and NVRAM loading,
brcmfmac's msgbuf protocol), modelled on an earlier port's approach (`ref/refport-os/wifi`: Linux's brcmfmac and exynos_pcie inside
XNU through a ~4,700-line compatibility layer) and the Linux driver. Used by the Windows Wi-Fi driver (the driver
runs the PCIe controller itself, since Windows cannot enumerate it; NDIS/WiFiCx on top) and by Starbite OS.
Firmware and NVRAM are read from VENDOR, never redistributed. Doc: `docs/WIFI-BCM4361.md`.

## D. Windows Mali GPU driver (background session)

From what works: our XNU StarbiteMali and the Metal bridge on iOS 26, Mesa Panfrost, and wddm-mali-g52 (an open WDDM
driver for a sister Bifrost GPU) as the template. Stages: a temperature watchdog first; a display-only driver for
DECON (modes, brightness); the Mali running jobs under Windows; Direct3D 11 through Mesa (research: never done on this
GPU). Doc: `docs/WIN11-GPU.md` (extends docs/STARBITE-MASTER-PLAN.md 3.8).

## E. Ultimate Utility OS (background session)

docs/UTILITY-OS.md grows: keyboard features, NFC, radios and antenna tools, every sensor (accelerometer, gyro,
magnetometer, barometer, light, proximity, heart rate, fingerprint/iris presence, temperatures), more tools.
Read-only towards the phone's identity areas, as today.
