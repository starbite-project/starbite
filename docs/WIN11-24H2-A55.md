# Windows 11 on the S9's cores: 23H2 on all 8, and what 24H2/25H2 would need

Status 2026-11-07 night: emulator crash proven (CNTFRQ_EL0 = 0, xtajit's TSC scaling) with a registry fix
(E1); a mixed A55 + M3 Windows proven impossible as is (LSE atomics); next section. The 24H2 part below is the 2026-11-03 assessment.

## 23H2 on all 8 cores and the x86/x64 emulator (2026-11-07, night)

Branch `claude/laughing-pare-2ca469` (on top of the big-core work of `claude/win-usb-host-7efe60`,
docs/WIN11-BIGCORES.md). Windows here is 23H2 (22631), which runs on ARMv8.0, so the M3s can join;
the 24H2 assessment below still holds for 24H2.

### The emulator crash: proven (CNTFRQ_EL0 = 0), fixed by a registry value

Windows' Application log (results-w2): 14 crashes since 2026-10-26, every one in **xtajit64.dll
10.0.22621.7582 at +0x30C70, 0xC0000094**, in DllHost, backgroundTaskHost, tzsync: any process that loads
x64/ARM64EC code dies while the emulator starts; OneDriveSetup (x86) the same, so Steam's 32-bit installer too.

From the DLLs pulled read-only (X1, build/win/xta-x1/):
- xtajit64.dll +0x30C5C `mrs x8, CNTFRQ_EL0`; if the counter is slower than the emulated TSC
  (MHz × 1,000,000; 1600 MHz by default) it computes the scale `udiv x9, x10, x9` with x9 = CNTFRQ; MSVC's zero
  check before it is `brk #0xF004` at **+0x30C70**, Windows' 0xC0000094. CNTFRQ_EL0 is 0 on this phone (S-Boot never
  sets it, only EL3 can; the woa firmware patches the kernel's copy to 26 MHz, but the emulator reads the register
  itself). The block runs only when KUSER_SHARED_DATA+0x3C6 (QpcBypassEnabled) is set, as it is here.
- xtajit.dll (x86, WoW64) has the same code: `mrs` at +0x45A40, `brk #0xF004` at +0x45A54.
- Both read a setting first, **`ScaleRdtsc`** (REG_DWORD: NtQueryValueKey, type 4, 4 bytes) from
  `HKLM\SOFTWARE\Microsoft\Wow64\amd64\xtajit64` resp. `...\Wow64\x86\xtajit` (a per-app subkey first, then
  the key). **0 returns before the division** (xtajit64 `cbz w19` +0x30C30, xtajit `cbz w19` +0x60C98); RDTSC then
  counts the raw 26 MHz timer. 1 uses the processor's MHz, anything else is the MHz: both still divide.
- `Wow64\amd64` doesn't exist on this install. ntdll reads it (0x18019E6D8) only for the x64 emulator's DLL
  name, a named value and then the default value, falling back to "xtajit64.dll" when either the key or the value
  is missing; a key without values changes nothing.

The PPTT has nothing to do with it. Fix: `tools/win/hive-scalerdtsc.py SOFTWARE OUT set` on an offline SOFTWARE
hive (hivexsh in the VM, like hive-service.py; refuses a dirty hive; `remove` undoes it). Phone request E1.

### The PPTT Windows expects

All shipping Qualcomm Windows devices carry the same PPTT shape (Yoga C630 / SDM850, Surface Pro X,
ThinkPad X13s, Windows Dev Kit 2023, XPS 13 9345; github.com/aarch64-laptops/build misc/*/pptt.dsl):
revision 1; one physical-package node holding an ID structure; one processor node per core, flags 0x2
(ACPI ID valid), parent the package, no cluster nodes; cache structures with **flags 0 and every
field 0**, shared by all cores (two level-1 nodes whose "next level" is one level-2 node, plus a
level-3 node on the package). So Windows reads the geometry from the CPU (CLIDR/CCSIDR) and only takes
the cache *nodes* from the table. Our build-time PPTT of 2026-11-07 (PpttBuild: revision 3, 28-byte
caches with valid geometry, clusters) gave an early 0x7E; that combination exists on no OEM device.

`tools/woa/pptt-gen.py` builds the S9's table in the OEM shape (482 bytes), with one change: the core
types have different depths (A55 CLIDR 0x82000023: L1 I+D, L2; M3 CLIDR 0x0B200123: L1 I+D, L2, L3),
so each type gets its own placeholder chain (A55 L1I, L1D -> L2; M3 L1I, L1D -> L2 -> L3) and nothing
hangs off the package. UIDs as the MADT: A55 0..3, M3 4..7. `--valid` would fill the A55 geometry
(measured) but is off. `pptt-patch.py --table` and `pptt-swap.sh IN.bin OUT.bin` put it into any image
(dxe-diff: only the platform ACPI file `11111111-…-501` replaced); `build-win-usbhost.sh PPTT_OEM=1`.

### All 8 cores

What the tables already say (release "P" MADT at ReadyToBoot, seen in B3 v1, and the DSDT):
- GICC UIDs 0..3 = A55 0..3 (interface 0..3, MPIDR 0..3, parked by the release BDS, mailboxes
  0xBBC70000.., v1), UIDs 4..7 = M3 0..3 (interface 4..7, **flags 0**, MPIDR 0x100..0x103, no
  mailbox, efficiency class 0; the A55s have 1, which is backwards: a higher class is a faster core).
- The DSDT has eight processor devices CPU0..CPU7 (ACPI0007, _STA 0xF) whose `_MAT` holds a GICC copy
  with parking version 0 (PSCI) and MPIDR 0x100..0x103 for the M3s: **Samsung's PSCI targets**. woa
  meant Windows to start the M3s by PSCI through its EL2 shim; it never worked because the M3s need
  XNU 0304's PMU writes first (B1).
- The MPIDR values are P's, not the real affinities (A55 n = 0x81000n00, M3 n = 0x8000010n), and
  Windows runs the A55s with them, so Windows doesn't compare them with MPIDR_EL1. They are unique, so
  the "A55 1 / M3 0 both 0x100" collision (section 1 below, WC2) never reaches the table.

The woa PSCI shim (relmods/Star2LtePsciEl2ShimStage0Proven, disassembled 2026-11-07): an 0x1104-byte
EL2 payload copied to 0xBBC11000 and installed with Samsung SiP SMC **0xC2000400** (x1 entry =
base + 0x1800, x2 0x2000, x3 1, x4 base, x5 0x8000); the payload sets VBAR_EL2 and HCR_EL2 |= TSC on
**the calling core only** and returns to EL1 with SMC 0xC2000401. It then answers PSCI_VERSION
(1.0), PSCI_FEATURES and AFFINITY_INFO itself and rewrites CPU_ON: the target and entry go into an
8-slot table, the core is started at the payload's trampoline (+0x2080, slot index as context id),
which checks MPIDR_EL1 against the slot and branches to the real entry. Secondaries never run the
EL2 setup, so trapping ID registers (HCR_EL2.TID3) on all cores would need that SMC per core.

Design (`Cores8.c` + `Cores8ParkStub.S` in Star2LteSsdtDxe, `STARBITE_CORES8=1`: M3 1..3, `=2`: also
M3 0 last):
1. During dispatch, before the shim (B2/B2b's proven path): per M3 core one reserved page as its ACPI
   parking-protocol mailbox, a 160-byte stub in its firmware half (arrival mark, event stream, WFE,
   mailbox check: CpuId == UID and JumpAddress != 0 -> JumpAddress = 0, jump with x0 = mailbox), the
   six PMU writes, ONE CPU_ON (target 0x100 + n). Stop at the first core that doesn't arrive in 200 ms.
2. At ExitBootServices, the live MADT in place: parked M3s' GICCs Enabled, parking v1, their
   mailboxes, efficiency class 1; A55s class 0; the DSDT's `_MAT` copies of those M3s replaced by the
   new entries; both checksums. Each core's zone-0 line `=C8 park core n … state S`: 1 parked, 2 taken
   by Windows.
3. BCD `numproc` 4 -> 8 (`tools/woa/bcd-numproc.py`: element 25000061 of the loader, one byte at file
   0x409c of today's BCD).

**Mixed A55 + M3 cannot run as is (ntoskrnl 22631, X1).** Proven from the kernel:
- The interlocked helpers (MSVC's outline atomics; ntoskrnl 0x14020D060.., one copy in every MSVC-built binary,
  drivers included) test a word at the start of their .data (ntoskrnl 0x140C00000). It is set on first use
  (0x14020E540): in kernel mode from **ID_AA64ISAR0_EL1.Atomic of whichever CPU runs that first call**, in user
  mode from KUSER_SHARED_DATA PF_ARM_V81_ATOMIC (0x296). If set, every later call uses LSE (`ldaddal`,
  `ldclral`, `casal`, …) on every CPU. The A55s report Atomic = 2, the M3s 0, so with any A55 in the system an M3
  sooner or later executes an LSE instruction = undefined instruction. Booting on an M3 (B3) doesn't help as long
  as A55 secondaries exist: each driver initialises its own copy on whatever CPU it first runs on.
- The boot-CPU feature code (0x1409D9CF4..) only ever sets KUSER_SHARED_DATA ProcessorFeatures bytes (crypto,
  CRC32, LSE, DotProd, JSCVT, LRCPC), never clears them.
- Secondary-CPU check (0x1409D9A2C..0x1409D9BB8): **bugcheck 0x3E** MULTIPROCESSOR_CONFIGURATION_NOT_SUPPORTED if
  a CPU's breakpoint count (ID_AA64DFR0 BRPs + 1, capped at 8; PRCB +0x898, set at 0x140286010), watchpoint count
  (WRPs + 1, capped at 2; +0x89C) or AArch32-at-EL0 support (ID_AA64PFR0.EL0 >= 2) differs from the boot CPU's.
- ntoskrnl never writes PSTATE.PAN.

So C3/C4 (A55 boot + M3 secondaries) are **not to be run**. What can work:
1. **Windows on the 4 M3s only** (the big cores): Windows boots on M3 1 (B3 v3 hand-off, docs/WIN11-BIGCORES.md),
   secondaries M3 0, 2, 3 (Cores8 parking), the A55 GICCs disabled. Every CPU is ARMv8.0, so the helpers pick
   LL/SC everywhere and the 0x3E check compares M3 with M3. Open: B3 itself (not yet run), M3 core 0's first
   CPU_ON, and Windows' PSCI calls from an M3 (no woa shim at EL2 there).
2. **All 8 with an EL2 ID-register trap**: HCR_EL2.TID3 on every A55 so ID_AA64ISAR0/ISAR1/MMFR1/PFR0/DFR0 read as
   the M3 ∩ A55 values. Needs our code at EL2 on each A55; the only known door is Samsung's SiP SMC 0xC2000400,
   which the woa shim uses once on the boot core. Unknown whether EL3 accepts it per core: a probe first.
3. The A55s only, as today (plus the emulator fix).

**Chosen 2026-11-07 (the user): option 1, Windows on the M3s.** `M3BOOT=3` + `CORES8` ("big"): M3Boot.c parks M3 1
for the B3 v3 hand-off; Cores8.c parks only M3 2 and 3 (`CORES8=1`, image big3: 3 CPUs) or also M3 0 last
(`CORES8=2`, big4: 4 CPUs) and exports their mailboxes (Cores8Mailbox); at the commit point on the M3, M3Boot writes
the MADT with M3 1 first, the parked M3s enabled (parking v1), all four A55s disabled, every efficiency class 0, and
syncs the DSDT _MAT copies to it (Cores8SyncMat). `numproc 4` stays. Images (build/woa/cores/, SOLO builds like B3
v3's: src38 + Star2LteSsdtDxe + SBGPU + the OEM PPTT): starbite-uefi-big3-gpu.bin 64dde9e9…, starbite-uefi-big4-gpu.bin
301be1eb…. Order on the phone: B3 v3 solo (620eace0) first, then big3, then big4 (request win-cores-BIG-request.md).

only, import libraries from .def files) built for ARM64, x64 and x86. An emulated build that prints

## The instruction set

- 24H2 (26100.x) and 25H2 (26200.x, the same core plus an enablement package) require **ARMv8.1
  atomics (FEAT_LSE)** on ARM64. ARMv8.0 parts (Snapdragon 835, Cortex-A72 in the Raspberry Pi 4)
  stop booting at 24H2.
- Measured on this S9 (NOTES.md 2026-10-28, from Linux): **M3 lacks PAN, LSE, RDM, DotProd, FP16,
  LRCPC, DPB**. The Cortex-A55 is ARMv8.2-A and has all of them. Whatever subset of v8.1/v8.2 24H2
  ends up needing, the A55 cluster covers it and the M3 cluster does not. So 24H2 has to run **only
  on the A55 cores**, and no M3 core may ever run Windows code.
- The boot CPU is A55 core 0 (MPIDR 0x81000000), so the loader and the early kernel already run on an
  LSE-capable core.

## What we have today (23H2 / 22631.7584 on src38)

- Windows sees and runs **4 CPUs** (WWR1 witness "4/4 CPUs") with `numproc 4` in the BCD.
- The A55 secondaries are started by the firmware, not by Windows. The published BDS (`STAR2LTE_PSCI_PARK`)
  does PSCI CPU_ON for Samsung's targets 1, 2, 3, parks each core in a polling stub, and publishes
  the mailboxes in the MADT (ARM parking protocol). "CPU_ON for MPIDR 0x100 never returns and takes
  the SoC down" (woa comment), so the M3 cluster is never touched.
- The source MADT (Madt.aslc) lists 8 GICC entries: A55 MPIDR 0x0..0x3, M3 0x100..0x103, all
  ENABLED (`STAR2LTE_LITTLE_CLUSTER_ONLY 0`), EfficiencyClass M3=0 / A55=1. The PPTT has 2 clusters
  of 4. The release DXE volume replaces this at runtime with its own "P" module (strings
  `SMP!SMP1`, `XSDT`, `APIC`, `FACP`), whose output has not been seen yet.

## What must change

### 1. MADT: only the four A55 cores, with their real MPIDRs

The **real** affinities are A55 core n = `0x81000n00` (MT=1, core number in Aff1) and M3 core n =
`0x8000010n` (no MT). In the Aff3..Aff0 fields that Windows compares, **A55 core 1 and M3 core 0 are
both 0x100**. An 8-entry MADT is therefore ambiguous no matter what, and the source table's 0x0..0x3
for the A55s is wrong for cores 1-3 (it only works today because the parking protocol, not a
Windows CPU_ON by MPIDR, brings them up, and `numproc 4` keeps Windows away from GICC 4-7).

For 24H2:

| GICC | AcpiProcessorUid | MPIDR (MADT) | Flags | EfficiencyClass | Start |
|---|---|---|---|---|---|
| 0 | 0 | 0x000 | ENABLED | 0 | boot CPU |
| 1 | 1 | 0x100 | ENABLED | 0 | parked, mailbox (PSCI target 1) |
| 2 | 2 | 0x200 | ENABLED | 0 | parked, mailbox (PSCI target 2) |
| 3 | 3 | 0x300 | ENABLED | 0 | parked, mailbox (PSCI target 3) |

The M3 entries are **removed**. They are not just flagged disabled, because ACPI 6.5's
Online-Capable bit and hot-add paths should not be able to reach them. The PPTT shrinks to one cluster
node with 4 leaf cores (UIDs 0-3); drop the M3 cluster node. Keep the parking protocol: Samsung's EL3
uses its own target numbering (1..3 for A55, 0x100.. for M3), which differs from the MPIDRs, so a
Windows-issued PSCI CPU_ON with MADT MPIDRs cannot work as is.

**Implementation**: a small DXE driver for the release volume (`dxe-replace.py --add`, the same way
as the src38 RTC module). It runs after the P module's table install (ReadyToBoot), finds the MADT
and PPTT through EFI_ACPI_SDT_PROTOCOL, and rewrites them in place: drops the GICC 4-7 entries,
corrects the MPIDRs, then fixes the length and checksum, and does the same for the PPTT. Then
`acpiview -s APIC` / `-s PPTT` in the UEFI Shell entry (docs/UEFI-SHELL.md) checks our source tables,
and `tools/woa/winpe/acpi-dump.ps1` in Windows dumps what the release really publishes. **First test
step: run acpi-dump.ps1 on 23H2 and read the release MADT** (MPIDRs, flags, parking mailbox fields).
The same table also suits 23H2, so the change can be proven on the working install before 24H2 exists.

### 2. Build-specific firmware code: the real blocker

The release DXE is matched to 22621.7582 / 22631.7584. It carries build-specific code: the
winload/ntoskrnl in-memory patches (`=NTPATCH n=08` in the ring) and the `Winpe22621RuntimeFrequency`
module. The reason it exists: **S-Boot leaves CNTFRQ_EL0 = 0** (NOTES.md:131), only EL3 can write it,
and Windows takes the timer frequency from that register. The published source finds the CNTFRQ patch
location from PE section geometry ("0x5A9C00 on 22621 and 0x549E00 on 19041"), so it was written to
generalise, but 26100 has never been tried, and the release binary is not the published source. A 26100 port needs:

- the CNTFRQ fix re-derived for 26100's kernel (the frequency is 26 MHz, as for Linux and iOS),
- the other in-memory patches the release applies, checked one by one against a 26100 boot (the
  =NTPATCH count, =EBSOK, then the latches),
- the woa catalog has no 26100 image (their installer test maps 26100.4061 to the 22621.7582 image
  with "may stop at the Samsung logo").

None of this can be done offline without the 26100 binaries and a device loop. It is the same per-build
work that took W5 two days for 22631.

### 3. Things that stay

- GTDT, the GIC (v2, GICC 0x10102000), the DSDT devices, the UFS/touch/HSI2C drivers (built against
  the 10.0.26100 WDK already, ref/exynos9810-woa/drivers/*.vcxproj), the RAM stages (3.4 GB as
  boot-services data), the PMIC RTC, and the shim's RWD1/P3 handshake.
- BCD: `numproc 4` stays (a belt to the MADT's braces), testsigning, hypervisorlaunchtype off,
  vsmlaunchtype off. Note: 24H2 turns VBS/HVCI on by default on capable hardware. With no EL2
  available (Samsung's uH owns it), the hypervisor-off settings matter even more.
- Where it lives: a 26100 VHDX on the WINDOWS partition with native VHD boot and its own BCD entry
  (STARBITE-2-PLAN section 6). It is selected per menu entry with the BCD-default DXE designed in
  docs/WINPE-ARM64-PLAN.md.

### 4. Media and disk

A 26100 ARM64 image via UUP dump is about 5 GB to download and about 15 GB to convert. The Mac has
12 GB free and the lima disk never shrinks. Convert on a host with space, or on the phone's
Windows, then bring the VHDX over on the SD card (the 22631 route: redeploy-from-sd.py).

## Windows 10 note (all 8 cores)

19041/19045 need only ARMv8.0, and the woa source already knows 19041's CNTFRQ location. 8 cores still
hit the MPIDR collision above (A55 core 1 = M3 core 0 = 0x100) and the M3 CPU_ON hang. "All 8 cores
on Windows 10" therefore needs Samsung's PSCI targets for M3 and a MADT that can tell the clusters
apart. Aff fields alone cannot, so this stays a stretch goal.
