## 1. Why x86/x64 apps fail on the big-core entry

### In plain words

Windows runs Intel-style (x86/x64) programs through a built-in translator, the
emulator (`xtajit64.dll` for 64-bit, `xtajit.dll` for 32-bit). The big cores
(Exynos M3) are an older generation of ARM than the small cores (A55). They lack a
few newer instructions, mainly the "fast atomic" family (LSE) and a lighter memory
barrier load (LDAPR). We assumed the emulator uses these newer instructions
unconditionally, so patching them out of the emulator DLLs looked like the fix.

**Disassembly shows that is not the case.** Microsoft's emulator already checks the CPU
before it uses any newer instruction, and on the M3 every one of those checks
correctly picks the old-style code. A patched copy of the emulator would behave
exactly like the original. So something else runs an instruction the M3 cannot run,
or a different error triggers the same crash. The leading suspect is the emulator's
**saved translation cache** (`C:\Windows\XtaCache`). Both entries boot the same Windows
install. Translations made while running on the A55 contain the fast atomic
instructions, because the A55 has them. Those saved translations are then reused on
the M3, where they crash. This is not proven yet. One cheap test (clear or disable
the cache on the big-core entry) confirms or rules it out without patching anything.

### Technical detail

**Symptom.** Every emulated process on the M3 entry fails with `c0000409` before it
prints anything: sbcpu-x64, sbcpu-x86, SysWOW64 cmd.exe and steam.exe. For x64 the
WER report names `xtajit64.dll +0x36D6C`. No x86 crash has been tied to a module yet
(see C8 below).

**The crash site is the emulator's own fail-fast [V].** `xtajit64 +0x36D68 mov w0,#5`
followed by `+0x36D6C brk #0xF003` is `__fastfail(5)`. It sits at the end of the
exception handler `0x36910`. That handler is reached only through ntdll's emulator
callback (ResetToConsistentState: EC export `0x10C0` -> `.a64xrm 0x33C0` -> `0x18968` ->
`bl 0x36910`), and only while the thread's emulator state is active (TEB+0x1788 -> +0x30,
flag +0x58). Three routes lead into the fail-fast [V]:

| From | Condition |
|---|---|
| `0x36C44` | ExceptionCode `c000001d` (illegal instruction), the faulting word is not one of the emulator's own markers `BRK #0xF00E..#0xF013`, and `0x366D8` did not convert it |
| `0x36BDC` | marker `BRK #0xF012` with CONTEXT.X15 > 0xFF |
| `0x36C60` / `0x36C6C` / `0x36C78` | any other unconverted exception that is not a write access violation on an 8-byte-aligned address |

So "illegal instruction" is the most likely cause but **not proven [I]**. At the `brk` the
evidence is still in registers [V]:
- `x19` = EXCEPTION_RECORD* (code at +0x0, ExceptionAddress at +0x10);
- `x25` = native ARM64 CONTEXT* (Pc at +0x108);
- `[x29+0x14]` = the faulting instruction word (route `0x36C44` only).

`xtajit.dll` has the same handler [V]: `+0x3B8AC..+0x3B8D4` compares the code with
`c000001d` and reads the word at Context.Pc (+0x108), using the marker table at
`0x3BB10`. The fail-fast is at `+0x5EF64 mov w0,#5` / `+0x5EF68 brk #0xF003`. The
predicted x86 crash offset is therefore `xtajit.dll+0x5EF68` [I].

**Every newer-than-ARMv8.0 instruction in the emulator is gated, and every gate is off on
the M3 [V].** The M3 values are taken from `build/woa/cores/big3-run1/cpu.log`:
PF set `2 12 18 19 23 24 25 27 29 30 31` (no 34); CP 4000/4030/4031 = `0x531F0020` / `0x11120` / `0`.

| Module, RVA | Instruction | Gate |
|---|---|---|
| xtajit64 `0x52B4-0x563C` (10) | outline atomics `ldaddal/cas/casal/ldset/ldclr...` | latch `[0xEF010]`, `tbz w16,#0` -> LDAXR/STLXR; init `0x5680` reads KUSER `0x7FFE0296` (PF34); M3 latch = `0x80000000` |
| xtajit64 `0x58E0-0x5F4C` (13) | `casal/caspal` misaligned bodies | dispatcher `0x56D0`: index `(addr&0xF)|(latch<<4)`; LSE rows used only when the latch bit is 1 |
| xtajit64 `0x13BFC-0x140A0` (15) | `cas/casp/swpb/swph/swp` JIT LOCK helpers | only reached through helper-table slots chosen at `0x6DBA0/0x6DBD8` (and `0x6E1F8/0x6E2C8/0x6E4EC`) from `state+0x20796` = PF34 && `ArmV81Atomics` (written `0x30A4C`) |
| xtajit64 `0x159D0`, `0x159E4` | `casal`, `ldsetal` (SRW) | 5 call sites in `0x2E2A0/0x2E2E8/0x2E360/0x2E408`; each does `ldrb [0xF1207]; cbz` (byte = RtlIsProcessorFeaturePresent(0x22), stored `0x1824C`) |
| xtajit64 `0x601D8`, `0x781B0` | CFINV/RMIF emitters (FlagM) | `ldrb [state+0x20799]; cbz`; set from CP4030[55:52] |
| xtajit64 `0x30220-0x30270` | memory model | `0x2008` (LDAPR) only with LRCPC or option `LdaprStlr`; M3 gets `0x4000` |
| xtajit64 `0x5690` | `mrs x16, CurrentEL` at EL0 | handled by the kernel: ntoskrnl `+0x2BD320` sets Xt=0, PC+=4 |
| xtajit64 `0x30C5C` | `mrs cntfrq_el0` (0 on the M3) | skipped when `ScaleRdtsc=0`, else `brk #0xF004` at `0x30C70` |
| xtajit64 `0x371FC-0x37250` (13) | `cas/casp/swp/ldapr` words | data: comparison constants of the fault classifier `0x36E98` |
| xtajit `0x105C..0x1330` (11) | outline atomics | latch `.data 0xE3010`, init `+0x13C0`; same scheme |
| xtajit `0xB358..0xB738` (13) | `cas/casp/swp*` V81 glue | selectors `+0x46EF8`, `+0x471FC`, `+0x4BBBC` on `+0x47B36` = PF34 && ArmV81Atomics |
| ntdll native `0x1122C`, EC `0x174370/0x1745A0/0x174980`; kernelbase `0x905C`, EC `0x15A710`; wow64 `0x105C` | LSE | same KUSER PF34 latch pattern |

Counted lse-scan hits that are real code paths: xtajit64 40 (10 outline + 13 misaligned
+ 15 JIT helpers + 2 SRW). The remaining hits are data. ntdll: 76 latched + 17
jump-table bodies. None of them run on the M3.

**Registry overrides can force instructions back on [V].** xtajit64 reads options
under `HKLM\SOFTWARE\Microsoft\Wow64\amd64\xtajit64`. If absent the defaults are
Opt4=1, Opt5=3, Opt7=0, ArmV81Atomics=1, and ArmV81Atomics is still ANDed with PF34.
- A negative `Opt5` (bit 31 set) with bit0/bit1 turns on AXFLAG (`state+0x2079A`) or FRINTTS (`+0x2079B`).
- A negative `Opt7` turns on AFP (`+0x2079C/D`, CP4039 bits [47:44]).
- `LdaprStlr` forces memory model `0x2008` (LDAPR) without LRCPC.

Leftover values like these on the phone would cause exactly this crash. They have to be
checked (step T1).

**Saved translation cache [I, strong].** xtajit bakes the chosen atomic helper into
generated code at translation time: helper offsets `0x480/0x488/0x458` (LSE) vs
`0x470/0x478/0x440` (LL/SC) are loaded at `+0x46F2C` / `+0x4BBD4` and passed to the
emitter `+0x23E58` [V]. The selector byte `+0x47B36` is read only at the three
selectors and at `+0x41844`. It feeds no header field or hash. The cache file
writer (`+0x78490..+0x78944`, magic `BLCK`/`XTAC`) stores no host-feature field [V].
So a translation made on the A55 can contain CAS/SWP calls. If the XtaCache service
hands it back on the M3, the result is `c000001d` inside emulated code, then
`__fastfail(5)`. That matches every symptom. Two things are **not verified**:
whether the XtaCache service itself rejects caches made on another CPU, and whether
xtajit64 keys its cache on the compile-flags word (built at `0x300D0`, used from
`0x48A9C`).

A second fail-fast in xtajit [V code, I relevance]: `+0x3F5E4..+0x3F5FC` compares child
and parent emulation flags under mask `0xBFFF7008`. That mask includes the memory-model
bits `0x2008` (A55) / `0x4000` (M3). A mismatch ends in `brk #0xF003` at `+0x5F8B4`.

**Unrelated to the emulator:** `winsqlite3.dll` 3.51.1.0 has unconditional ARMv8.1/8.3
code [V]: `casal` at `0xEC594`, `0xEC614` and `0xEF098` (the LL/SC tail at `0xEF0A4` is
unreachable), 92 LDAPR in total, and 27 unguarded LDAPR in its ARM64EC part
(`+0x142CAC ldapr w8,[x8]`, `+0x14846C ldapr x8,[x0]`). Any process that calls into it
dies on the M3, whichever emulator is used. Replacing that file is out of scope (it is
a Windows file).

**How Windows picks the x64 emulator [V]** (ntdll `0x19E6D8`, called from
LdrpLoadXtaBase `0x19F018`/`0x19F050`):
1. It opens `\Registry\Machine\Software\Microsoft\Wow64\amd64`.
2. It queries the value named after the process's EXE (BaseDllName at `[0x349428]+0x58`; that this global is LdrpImageEntry is [I]).
3. It then queries the default value `""`.
4. Otherwise it uses the built-in `xtajit64.dll` (`0x2E3878`).

The value must be REG_SZ or REG_EXPAND_SZ. A name without `\` gets the System32
prefix; a full path is used as is (`wcschr 0x5C` at `0x19E844`). After loading,
`0x19F0D8` requires LDR flag bit 25 (CHPE/ARM64EC image), else `c000007b`. Twenty
exports are resolved from table `0x2E32A0`; only BeginSimulation, ExitToX64,
RetToEntryThunk and DispatchJump are required. No signature check was found in this
code. Whether the underlying image load (`0x19C580`, flag `0x08000000`) or a
code-integrity policy demands a Microsoft signature is **not known**.
For x86, wow64.dll (`0xEA20`) reads `Wow64\x86` and has no built-in fallback [V].
A renamed copy still reads its options from `...\amd64\xtajit64` (hard-coded string) [V].

## 2. Options, ranked

Ranked by likelihood of success times effort. The user's preferred route, DLL patching,
is A2. It is ranked behind A1 because, per section 1, patching the emulator's known
LSE sites cannot change anything on the M3.

### A. Microsoft's emulator on the M3: configuration first, patched copies only if a dump points at them

**A1. No patch: clear the cache, check the registry (most likely, least effort).**
- What is done: on the big-core entry, (a) remove any forcing overrides (negative Opt5/Opt7, LdaprStlr, LdaprDmb) and make sure `ScaleRdtsc=0` exists under both `amd64\xtajit64` and `x86\xtajit`; (b) stop and disable the XtaCache service and move `C:\Windows\XtaCache` aside, or set `JitCache=0` under `amd64\xtajit64` (semantics [I]: byte `+0x206E4` read at `0x30450`).
- What could block it: the cache may not be the cause (the XtaCache service may reject foreign caches); then A1 fails and the dump (T3) is needed.
- Effort: one or two boots, offline hive edits, no code.
- What the user gets: x64 **and** x86 apps on the big cores with Microsoft's unmodified emulator. The cost is slower first starts, plus either a cache clear whenever the entry changes or XtaCache kept off on the big-core entry.

**A2. Patched renamed copy of xtajit64/xtajit (only if the dump shows an unguarded word inside emulator host code).**
- What is done: a same-size byte patch in a copy (e.g. `xtajit64m3.dll`). LDAPR becomes LDAR 1:1, which is a stronger and therefore valid substitute:
  - W `0xB8BFC000` -> `0x88DFFC00`
  - X `0xF8BFC000` -> `0xC8DFFC00`
  - H `0x78BFC000` -> `0x48DFFC00`
  - B `0x38BFC000` -> `0x08DFFC00`

  (Rn and Rt fields are kept.) An LSE op becomes a branch to an LDXR/STXR loop in `.text` slack (`0x18A` bytes free [V]) or in a new section, with `.pdata`. A gate byte is forced off with a same-size store (e.g. `+0x30F58 strb wzr`). The copy is selected per EXE (value `sbcpu-x64.exe` under `Wow64\amd64`); the default value is used only after that passes.
- What could block it:
  - The fault is in JIT output from an emitter. Patching an instruction encoder is a much bigger job; prefer C.
  - The fault is in a System32 ARM64EC DLL. That is excluded, because Windows files are not modified.
  - A code-integrity policy (Smart App Control, WDAC/App Control, MicrosoftSignedOnly) rejects the unsigned copy. **Stop there; no bypass.**
  - The copy must keep the ARM64X/CHPE metadata (bit 25), the EC export table (native export dir empty; DVRT swaps in `0xEC120`) and CFG (DllCharacteristics `0x4160`, no FORCE_INTEGRITY [V]).
- Effort: small for a handful of words (a day with host verification); large for emitters.
- What the user gets: the same as A1, but with our own copy that has to be kept in step with Windows updates.

### B. Generic rewriter for every module that needs it
- What is done: a tool that rewrites every unguarded LSE/LDAPR in any PE (trampolines plus `.pdata`), applied to copies.
- What could block it: the modules that actually need it (winsqlite3, possibly other System32 EC code) are Windows files that load by fixed name from System32 or KnownDLLs. Running a modified copy would mean replacing or redirecting system files, which is out of scope. The emulator itself does not need it (section 1).
- Effort: large (correct trampolines, unwind data, ARM64X relocation pages, CFG tables).
- What the user gets: nothing beyond A2 for emulation. Keep it as the A2 patch tool, scoped to our own copies; no general rewriter.

### C. FEX's Windows module (`libarm64ecfex.dll`) in place of xtajit64, x64 only
- What is done:
  - Build FEX (source checked at `e3b30dd`) for ARM64EC with `-DTUNE_ARCH=generic -DTUNE_CPU=none` (the default `TUNE_CPU=native`, CMakeLists.txt:201, would put the build host's LSE/RCPC into FEX itself [V]) and `-DUSE_PDB_DEBUGINFO=True`.
  - Add three local patches:
    - **Patch A**, syscall numbers for 22621/22631: 23H2 ntdll does not export `__arm64ec_syscall_ffs`, so `GetNTSyscallNo`/`InitSyscalls` (Module.cpp ~299-317) fail. Use a table keyed on PEB OSBuildNumber, taken from the native ntdll stubs: `0xF7A0 svc #0x43`, `0xF4F0 #0x18`, `0xF870 #0x50`, `0x10A90 #0x172` [V]. The EC stubs `0x18B790/0x18BFC0` are wrappers and cannot be decoded.
    - **Patch B**, CNTFRQ_EL0 = 0: set CycleCounterFrequency to 26 MHz at its init in SpinWaitLock.cpp and CPUID.cpp. This also fixes the third division at SpinWaitLock.h:73.
    - **Patch C**, exception stack layout: drop `Pad[4]` from KiUserExceptionDispatcherStackLayout (Module.cpp:366-372) below build 26100. 23H2 reads the record at `+0x390` (native `0x12740 add x0,sp,#0x390`; EC `0x175720 add x0,sp,#0x860` = 0x4D0+0x390 [V]). Every FEX guest syscall goes through this path.
  - Select the DLL per EXE by full path.
- What could block it:
  - Nobody has run FEX on 23H2 or on an ARMv8.0 Windows device.
  - Other ARM64EC interface differences between 23H2 and 24H2 may exist.
  - A crash in System32 EC code or winsqlite3 hits FEX the same way.
  - Code-integrity policy (stop if so).
  - No 32-bit: FEX's WoW64 module hangs on real Windows [S].
- Effort: medium-high (toolchain setup in Lima, three patches, host checks, then a few boots).
- What the user gets: x64 apps on the big cores with an emulator we control and can debug. Its ARMv8.0 support is documented: LDAXR/STLXR for CAS, LDAR for LDAPR [S]. FEX's x64 performance on Windows vs xtajit64 is unknown.

### D. x86 apps through Starbite's Linux layer (FEX + Wine)
- What is done: run FEX on Linux in Starbite OS with an x86/x64 rootfs and Wine; Steam runs as Linux or Windows apps there.
- What could block it: depends on Starbite's Linux layer (kernel, Mesa/GPU, display). Starbite needs the GPU work the user mentioned, and Wine games need a working GPU path. FEX on Linux supports ARMv8.0 [S], but the M3 has not been tested with it here.
- Effort: large, but shared with the Starbite GPU and compositor track.
- What the user gets: both 32-bit and 64-bit x86 apps on the big cores, outside Windows. A longer-term route, not a fix for Windows.

### E. Keep x86/x64 on the normal (A55) entry
- What is done: nothing. Emulation already works there (ScaleRdtsc=0 fix).
- What could block it: nothing. But once the M3 entry has been used, the same cache problem may run the other way. A1's cache clear makes switching safe [I].
- Effort: none.
- What the user gets: working x86/x64 now, on the slower cores; big cores for native ARM64 only.

**Ranking:** A1 > E (fallback that works today) > A2 (only if the dump points into xtajit
code) > C (x64 only) > D (long term) > B (not worth building beyond the A2 tool).

## 3. First concrete steps

Every step that touches the phone or changes a Windows setting needs the user's OK,
and runs from the main session under its rules: one phone, verified backups,
`&&` between flash and boot, a dead-man for unattended boots. Prefer offline hive edits
and pulls from the host over commands inside Windows. Run attended unless the
big-core entry supports the unattended autotest (see that memory note).

### T0 (host only, before any boot)
- Pull read-only from the Windows partition (list: scratchpad `pull-list.txt`):
  - SOFTWARE and SYSTEM hives;
  - `Windows\XtaCache\` (listing with sizes and timestamps, plus the files);
  - Tier 1a (kernel32, apphelp, advapi32, msvcrt, sechost, bcrypt, rpcrt4);
  - Tier 1b (wow64base, wow64win, wow64con, win32u, `SyChpe32\*.dll`);
  - Tier 2 for Steam (ucrtbase, msvcp_win, user32, gdi32, gdi32full, imm32, combase, ole32, oleaut32, shell32, shlwapi, shcore, windows.storage).
- Read from the hives (no changes):
  - `Wow64\amd64` and `Wow64\x86` and their `xtajit64` / `xtajit` subkeys: Opt4, Opt5, Opt7, ArmV81Atomics, LdaprStlr, LdaprDmb, ScaleRdtsc, JitCache, and any per-EXE values;
  - `SYSTEM\CurrentControlSet\Services\XtaCache` (Start);
  - code-integrity state: `SYSTEM\CurrentControlSet\Control\CI\Policy` VerifiedAndReputablePolicyState (Smart App Control), plus any WDAC policy files under `Windows\System32\CodeIntegrity`.
- Scan the ARM64EC ranges of every pulled DLL with `skeptic/scan.py` + `tag.py` + `ctx.py` (latch or dispatcher pattern vs unguarded).
- Pass criteria:
  - no negative Opt5/Opt7, no LdaprStlr;
  - ScaleRdtsc=0 under both keys;
  - XtaCache holds files with A55-boot timestamps (supports the cache theory);
  - no unguarded LSE/LDAPR in the start-up EC code of the Tier 1a DLLs. Any hit there blocks A and C equally and is recorded as such.

### T1 (M3 entry, read-only): confirm the x86 crash site
- Run sbcpu-x86 once and read Application log event 1000.
- Pass: module `xtajit.dll`, offset `0x5EF68` (same unmatched-instruction path as x64). Anything else is noted and changes the plan for x86.

### T2 (M3 entry, one setting change): the cache test (A1)
- Offline, before the boot:
  - fix any override found in T0;
  - set XtaCache `Start=4` in the SYSTEM hive;
  - rename `Windows\XtaCache` to `XtaCache.a55`, so it can be restored.
- Run:
  - sbcpu-x64;
  - sbcpu-x86;
  - `C:\Windows\SysWOW64\cmd.exe /c ver`;
  - a freshly built x64 test EXE that has **never** run on an A55 boot. That is a discriminator: if this one also fails with the cache present, the cache theory weakens [I].
- Pass: all four print and exit 0; no new WER entries.
- Rollback: Start back to its old value; rename the folder back.
- If it passes: run Steam next. Check that steam.exe is x64/x86 (PE machine field) and does not load winsqlite3. Then decide per entry: keep XtaCache off on the big-core entry, or clear the cache when entries change.

### T3 (only if T2 fails): get the real faulting PC and word
- Offline SOFTWARE hive: `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\sbcpu-x64.exe` with:
  - DumpType = 2 (full);
  - DumpFolder (REG_EXPAND_SZ) = `C:\sbdumps`;
  - DumpCount = 2.

  Same for `sbcpu-x86.exe`. Run each once and pull the `.dmp` files read-only.
- Host parser (new, in the scratchpad): read the minidump streams ThreadList, Exception, Memory64List, ModuleList and MemoryInfoList. In the thread that stopped at `xtajit64+0x36D6C` (or `xtajit+0x5EF68`):
  - read `x19` -> ExceptionCode / ExceptionAddress;
  - read `x25` -> CONTEXT.Pc (+0x108);
  - read the DWORD at `x29+0x14`;
  - read the word at Pc from dump memory.
- Classify the region (image + RVA, private executable memory = JIT cache, XtaCache mapping) and the word (LSE, LDAPR, RDM, DOT, FP16, other). If ExceptionCode is not `c000001d`, follow the route table in section 1.
- Pass: one concrete (module or region, RVA, word, code) per process. This decides A2, C or a blocker.
- Rollback: delete the LocalDumps keys.

### T4 (A55 entry): prove per-EXE selection and loader acceptance before any patch
1. Negative test: value `sbcpu-x64.exe` = `C:\sbx86\doesnotexist.dll` under `Wow64\amd64`. Pass: sbcpu-x64 fails to start (load error) while other x64 apps still run. That proves the per-EXE value is read.
2. Positive test: a byte-identical copy at `C:\sbx86\xtajit64.dll` with the value pointing at it. Pass: sbcpu-x64 runs.
3. Then a copy whose only change is invalid Authenticode (the security directory removed, which a patched file has anyway). Pass: still runs. **If it is refused by code integrity, stop A2 and C (no bypass).**

- Rollback: delete the value.

### T5 (only if T3 points into xtajit host code): patched copy, A55 then M3
- Same per-EXE value, now pointing at the patched copy.
- Pass on the A55: no regression with sbcpu-x64. Pass on the M3: sbcpu-x64 prints and exits 0.

### T6 (if A fails or x64 needs an alternative): FEX
- Host build and the host checks below.
- A55 per-EXE run, then the same with `HostFeatures=disableatomics,disablelrcpc,disablelrcpc2` to simulate the M3.
- Then the M3 entry.
- Pass: sbcpu-x64 exits 0, and the FEX log in `%LOCALAPPDATA%` shows no fault.

### Patch tool design (for A2; host only)
- **Inputs:**
  - the original DLL plus its expected SHA-256 (from the read-only pull);
  - a patch spec (JSON) with one entry per site: `rva`, `expect` (original bytes), `new` (bytes or a trampoline template), `reason`, and the T3 dump evidence it answers.
- **Outputs:** a new file under a new name (never in place), a patch report (before/after disassembly per site) and the new SHA-256.
- **Rules:**
  - refuse if the input hash or any `expect` bytes differ;
  - same-size patches only, except trampolines placed in `.text` slack or a new executable section, each with a `.pdata` entry;
  - never touch ARM64X dynamic relocation targets (parse the DVRT first and refuse any overlap);
  - keep the load config, CHPE metadata and EC export table byte-identical;
  - recompute the PE checksum;
  - remove the now-invalid security directory (this does not get around any check; a policy that needs a signature still refuses the file).
- **Host verification before any phone run:**
  1. Parse with pefile; diff the two files and confirm that only the listed byte ranges changed.
  2. Disassemble every changed site with capstone and with llvm-objdump in Lima; trampolines must be LDXR/STXR loops with the same memory ordering (acquire+release for `*AL` forms).
  3. Re-run lse-scan, `scan.py`, `tag.py` and `ctx.py`. The patched sites must be gone, and the guarded counts must not change.
  4. Check that the 20 loader exports resolve through the EC export table, and that the CHPE metadata pointer and bit-25 preconditions still hold.
  5. Reapply the same patch to a second copy and require identical bytes (deterministic).

## 5. Result: the persistent translation cache was the cause; fixed by sbxta.sys (2026-11-11)

### In plain words
x86 and x64 programs work on the big-core entry. Windows keeps a disk cache of translated x86/x64 code (the XtaCache
service). That cache was built on the small A55 cores, which have newer instructions than the M3, so the M3 crashed
when it reused it. A small Starbite driver now switches that service off when Windows starts on the big cores and back
on when it starts on the small cores. No Windows file is changed. Apps start a little slower on the big cores (each
run translates again, nothing is reused from disk).

### Runs (main session; folders under `build/woa/cores/`)
| Run | Change on the M3 row | sbcpu arm64 / x64 / x86 / x64fresh | SysWOW64 cmd | Other |
|---|---|---|---|---|
| x86t2-2 (T2) | XtaCache Start=4, folder renamed to XtaCache.a55 | all exit 0 | runs | |
| x86t2b-1 (T2b) | XtaCache Start=4 only, A55 cache folder left in place | all exit 0 | runs | Steam client + steamwebhelper 150 s with a window, no Steam crash events |
| sbxta-run1, A55 boot | sbxta installed, Start 2 at install | all exit 0 | runs (7) | 0 application errors; State: A55, Midr 0x410FD051, Start 2 -> 2, status 0 |
| sbxta-run1, M3 boot | sbxta sets Start 2 -> 4 | all exit 0 | runs (7) | only the 10 known winsqlite3 events; State: M3, Midr 0x531F0020, Start 2 -> 4, status 0 |

So the folder does not have to move (T2b): the service being stopped is enough, meaning the emulator only uses the
saved translations through that service. The A55 -> 2 restore path is exercised by the next A55 boots (T38 cycles).

### The fix: `starbite/win/sbxta/sbxta.c` (WIN11-M3-CLEAN.md section 34)
- WDM driver, `Start=1` (system start: loads before the service control manager reads service settings), ErrorControl 0.
- Reads MIDR_EL1. M3 (implementer 0x53, part 0x002) -> `Services\XtaCache\Start` = 4. A55 (0x41, 0xD05) -> 2, only if
  it is 4. Anything else -> no change. `Parameters\DisableOnM3` = 0 turns the switch off.
- Logs to `Services\sbxta\State` (Boots, Midr, Cpu, XtaStartBefore/After, XtaStatus, Result).
- Folder swap (`Parameters\SwapCache`) exists but stays 0; T2b showed it is not needed.
- Build: `build/woa/cores/sbxta-1/sbxta.sys`, sha256 81ea774f9463e9a1b72b93e52966d0d0ea9759b69261d8b2cdf0b3c996830110,
  commit 42056cc, test-signed (Starbite Test Signing). Installed on the phone; pre-install SYSTEM backup is
  `backup/*-pre-sbxta`.
- Rollback: `tools/win/hive-service.py SYSTEM SYSTEM.new remove sbxta`, delete `C:\Windows\System32\drivers\sbxta.sys`,
  set `Services\XtaCache\Start` = 2.

### Answers to section 4
1. The cache is not keyed on host CPU features in a way that protects the M3: A55-made translations were reused on the
   M3. Stopping the service is enough to stop the reuse (T2b).
2. Not measured (no dump was needed). The c000001d reading fits, but it stays unproven.
6. x86 had the same cause: it passes with the same switch.
9. Steam ran on the M3 row for 150 s with a window in T2b. It did not hit the winsqlite3 problem in that run.
3, 4, 5, 7, 8, 10: open, but none blocks anything now.
